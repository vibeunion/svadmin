## 执行顺序

1. 读取用户需求及 `docs/product/health-office/PRD-v1.1.md`。V1.1 是 V1.0 的实施补充，不取消 P0/P1 一期需求。
2. 对每个改变说明：谁需要、要完成什么任务、失败后如何恢复。将未知内容标为假设，不冒充用户访谈结果。
3. 为故事定义前置状态、操作权限、数据范围、版本要求、处理原因和验收结果。关联 UI 编号及自动化测试名。
4. 先修改纯业务状态层并写失败测试，再连接 Svelte 页面。复用 svadmin 组件和语义 tokens，不增加 Tailwind、React、任意 HTML 渲染或公网 AI 调用。
5. 检查真实风险：原件覆盖、跨部门读取、危急任务漏处理、过期结果覆盖、误把 mock 当接入、敏感资料进入公开仓库。
6. 分别汇报“代码已写入”“交互已验证”“真实集成”“生产验收”。测试必须针对当前内容；不把演示数据的数值称为效果指标。

## 每次必查

预警已读不等于确认；确认不等于关闭。一级预警处置需要独立复核。原始文本不覆盖，校对建议必须匹配文本版本和原文区间。管理员不默认拥有报告或原件权限。检查失败、未执行和无法判定不能显示正常。

## 产物

维护 PRD 实施补充、故事与测试对应表、风险清单、实际验证报告。后端、原件存储、服务授权、生产数据、测评和部署需要单独准入；不可把前端演示升级宣称为生产系统。
