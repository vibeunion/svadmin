# 企业级后台产品规范

这份文档是 `DESIGN.md` 的业务落地层。`DESIGN.md` 规定视觉和组件语言，
本文件规定业务页面如何组织任务、数据、权限和反馈。

## 1. 先定义任务，再选择页面

每个页面开始前必须写清楚以下五项：

| 项目 | 必答问题 |
| --- | --- |
| 主要岗位 | 谁每天使用这个页面？ |
| 主要任务 | 用户进入页面后要完成什么？ |
| 判断依据 | 用户需要比较哪些字段或状态？ |
| 主操作 | 页面最重要的下一步是什么？ |
| 失败恢复 | 失败后用户如何继续，不丢什么上下文？ |

一个页面只能有一个主要任务。其他信息必须服务于这个任务，不能因为
“以后可能有用”而全部放到首屏。

## 2. 页面类型决策表

| 用户任务 | 页面模式 | 首屏必须有 | 不要放在首屏 |
| --- | --- | --- | --- |
| 找到并处理一批记录 | `ListPage` / `PagePattern list` | 状态筛选、搜索、关键字段、行操作 | 审计全文、技术 ID |
| 创建或修改一条记录 | `CreatePage` / `EditPage` / `PagePattern form` | 字段分组、校验、保存状态 | 无关统计、重复说明 |
| 查看一条记录并追溯原因 | `ShowPage` / `PagePattern detail` | 摘要、状态、主操作、最近变更 | 全部关联表 |
| 连续处理一个对象的多个阶段 | `WorkspaceLayout` / `PagePattern workspace` | 对象列表、当前对象、阶段动作 | 过多导航和重复标题 |
| 观察趋势并进入处理 | `DashboardPage` | 业务指标、异常、钻取入口 | 只有装饰没有动作的图表 |

资源 CRUD 优先使用 `ListPage`、`CreatePage`、`EditPage`、`ShowPage`。
只有自定义业务编排才使用 `PagePattern`。`PagePattern` 只负责布局和状态
呈现，不负责查询、权限、提交和业务决策。

## 3. 列表页标准工作流

列表页按以下顺序组织：

```text
页面标题 + 主操作
状态视图（可选）
搜索 / 筛选 / 保存视图
批量操作（仅在有选择时出现）
表格或列表
分页 / 总数 / 数据新鲜度
```

### 字段与操作规则

- 首屏优先展示：业务标识、当前状态、负责人或截止时间、下一步动作。
- 字段必须能帮助用户排序、筛选或做决定；不能只因为数据库里存在就展示。
- 行内只保留最高频动作，其他动作进入 `...` 菜单。
- 危险操作必须显示影响范围，并在确认完成前保持原页面上下文。
- 批量操作只对当前选择生效；跨页选择必须明确提示选择范围。
- 状态不能只靠颜色表达，必须同时有文字或图标。

### 列表状态矩阵

| 状态 | 页面内容 | 用户下一步 |
| --- | --- | --- |
| 初始加载 | 骨架或稳定占位，不跳动主操作 | 等待 |
| 初始为空 | 解释为什么为空 + 创建或导入入口 | 创建 / 导入 |
| 筛选无结果 | 当前筛选条件 + 清除筛选 | 清除 / 修改筛选 |
| 加载失败 | 失败原因范围 + 重试 | 重试或离开 |
| 无权限 | 权限边界 + 联系人或返回入口 | 返回 / 申请权限 |
| 有数据 | 表格、筛选、分页、行操作 | 处理记录 |
| 批量选择 | 选择范围、可用批量动作、清除选择 | 执行或取消 |

## 4. 反馈与状态归属

一个事件只能有一个主要反馈面：

| 事件 | 主要反馈 | 规则 |
| --- | --- | --- |
| 字段校验失败 | 字段下方错误 | 保留用户输入 |
| 普通保存成功 | Toast | 不再额外显示成功横幅 |
| 保存后进入完成态 | 页面状态 | 不重复发成功 Toast |
| 查询失败 | `DataState` / 错误反馈 | 不展示旧数据为当前数据 |
| 权限不足 | Forbidden 状态 | 不通过隐藏文案伪装成空数据 |
| 可撤销操作 | Undo Toast | 在撤销窗口内保持可恢复 |

页面组件拥有布局，业务组件拥有查询、权限、提交和数据状态。任何组件
都不得默认授予权限，也不得把演示数据或本地状态描述为已持久化。

### 查询错误的落地规则

- 已有错误态及重试入口的业务组件，内部查询设置 `errorNotification: false`，
  由内联反馈承接失败，不能同时弹默认错误 Toast。
- 主查询失败不能伪装成空列表；关联资料、追加页或子节点失败只标记失败范围，
  保留同一作用域内仍有效的已加载记录。重试只重新请求失败范围。
- 无内联反馈的 headless 查询保留默认通知。核心层为同一 Query 提供不透明
  `key`，内置 Toast 按 key 去重；自定义 `NotificationProvider` 应按 key
  更新或合并通知，不能假设 `open` 只调用一次。
- 不把查询参数、租户信息、meta 或原始错误放进自动生成的通知 key。
  显式通知文案、回调与业务自定义 key 保持调用方约定。

当前适用范围：`AutoTable`、详情页及详情抽屉、`InfiniteList`、SVAR 资源表格，
以及示例的 Todo、Domain、Operations、CRM 工作台、用户管理、房产、AI、
日历和 Mail 当前文件夹查询；
不代表所有业务页面均已完成迁移。CRM 还必须按当前资源和视图启用查询，
统计不得和主列表重复承接同一个商机查询失败。

用户管理的成员、角色、权限是公共摘要和名称依赖，不配置恒真 `enabled`；
账户、日志、设置按页面职责启用。角色列表不因成员或权限关联加载/失败而
消失，未知计数及权限明细不能显示为零或“尚未分配权限”。账户页不请求审计
日志，也不展示依赖该查询的风险指标；折叠摘要中未启用的统计显示未知占位，
不能使用其他页面遗留的缓存冒充当前值。依赖矩阵与回归证据见
`docs/evidence/user-management-query-scope-20261021.md`。

Mail 未读角标在收件箱页共享列表错误反馈，不另发通知；其他文件夹的收件箱
统计尚无内联重试入口，保留默认通知，不能把未知未读数量显示成零。该策略
必须随当前文件夹变化，不能只在组件初始化时确定。

房产四类页面只请求当前资源，视图参数不能改变资源归属。筛选无结果可
清除筛选返回列表，但不得删除收藏。收藏不可读不等于“没有收藏”，在恢复前
禁止覆盖；“今日看房”按全部当前看房记录的本地日期统计，不随搜索结果消失，
跨日及页面重新激活时刷新日期。证据见
`docs/evidence/property-query-scope-20261021.md`。

AI 模板和运行信息视图不请求隐藏的会话列表。列表未成功读取时保留问题，
但不调用助手、不创建或更新会话；查询错误由列表重试承接。日历整体内容
依赖同一查询，不在错误期间展示假零统计或“暂无日程”。

Dashboard 自有多个资源查询已有页面总错误、分区错误或未知占位时，
显式关闭默认查询通知；全局重试只重试失败查询，分区重试只重试对应查询。
角色等辅助计数同样区分未知与真实零值。刷新失败保留旧记录时必须标记
部分数据不可用，不能把缓存当作已同步指标。Dashboard 中的默认 Surface
组件使用统一本地化错误文案，并通过现有 `refresh(sourceId)` 恢复；
内置 SVAR Grid 同样纳入错误展示规范：明确拒绝访问显示“无权访问”，
查询或权限检查异常显示“数据不可用”，无效返回或绑定缺失显示“数据无效”。
界面不展示 Provider 原始诊断，`onError` 保持原有数据源错误契约，
不因展示层脱敏而改变核心既有的授权异常归一化或新增绑定错误事件。
新增安全文案字段保持可选，旧宿主消息对象仍可使用默认本地化值。
第三方 Widget 的错误展示和恢复仍需独立验收，不能从默认目录外推。证据见
`docs/evidence/dashboard-query-feedback-20261021.md`、
`docs/evidence/surface-query-feedback-20261021.md`。

### 写入反馈的落地规则

严格 `useCreate`、`useUpdateMany`、`useDeleteMany` 支持显式
`successNotification: false` / `errorNotification: false`，由调用页面接管
对应反馈；省略时保持原来的默认通知。此处只增加关闭选项，不声明支持字符串、
通知回调或其他 Hook，也不改变认证处理、审计、缓存刷新和写入结果。

AI 页面接管上述三种写入反馈：助手或保存失败保留问题；删除失败保留历史；
已保存但列表刷新失败只能重试读取，不能误报为保存失败或自动重写。
历史删除成功而收藏持久化失败必须明确提示部分完成，并只重试收藏保存。
实现及通知矩阵见 `docs/evidence/ai-calendar-query-feedback-20261021.md`。

CRM 查询验收：

```gherkin
Given 用户打开 CRM 客户账户
When 商机查询失败
Then 不请求隐藏的商机资源，客户列表保持可用且不显示全局通知

Given 用户打开 CRM 商机
When 商机请求仍在进行或失败
Then 只显示一个列表加载/错误状态，成功后再显示商机统计

Given 用户在 CRM reports/dashboard 查看统计
When 商机统计请求失败或重试
Then 客户记录等已加载内容保持不变，只重新请求商机统计
```

SVAR 资源表格的恢复验收：

```gherkin
Given 主查询失败
When 用户刷新后请求再次失败或恢复
Then 失败只显示一个内联错误且成功后移除错误

Given 窗口数据读取失败
When 用户点击重试窗口
Then 重新读取失败窗口而不重载首页

Given 追加页读取失败且已有记录有效
When 用户再次加载更多
Then 保留已有记录且只重新请求下一页

Given 子节点读取失败
When 用户选择已加载记录并重试子节点
Then 父记录仍可操作且仅重新请求该分支
```

上述每个场景在首次失败、再次失败和恢复后都必须验证通知 Provider 与内置
Toast 队列没有重复错误通知。回归入口：
`scripts/fixtures/svar-grid/resource-loading.spec.ts`。
当前真实引擎的单文件复验及覆盖边界见
`docs/evidence/svar-resource-query-feedback-20261021.md`。

`InfiniteList` 的追加页恢复验收：

```gherkin
Given 首屏请求失败且尚无有效记录
When 用户重试
Then 显示完整错误态且重新请求首页

Given 已加载记录且下一页请求失败或响应不符合契约
When 用户重试失败页
Then 原有记录及其节点保留且只请求失败的下一页

Given 追加页失败且自动加载哨兵已移除
When 之前排队的滚动回调再次到达
Then 不自动重试且错误提示保持可见

Given 用户重试追加页且请求尚未结束
When 用户连续点击或滚动回调再次触发
Then 同一页只保留一个在途请求且原有记录仍可用

Given 追加重试尚未结束
When 切换租户后旧请求成功或失败
Then 仅显示新作用域记录且旧响应不产生错误或通知
```

再次失败时仍保留记录及重试入口，恢复后移除错误并恢复正常追加。
所有状态均不得暴露原始错误或重复发送通知。此处只规定追加页失败的局部恢复，
不改变主查询刷新失败的完整错误态。回归入口：
`packages/ui/src/components/query-feedback-ownership.test.svelte.ts`。

## 5. 页面验收门槛

业务页面合入前必须完成：

1. 有一个明确的主要任务和一个主要操作。
2. 已选择正确的页面模式，没有重复标题或重复页面壳。
3. 已验证有数据、初始空、筛选无结果、加载、错误和无权限状态。
4. 已验证长标题、长字段、窄容器不会遮挡操作或产生不可解释的横向滚动。
5. 已验证键盘焦点、按钮名称、表单标签和状态文本。
6. 已验证成功、失败、权限和批量操作反馈各只有一个主要反馈面。
7. 真实业务页面使用真实权限和数据状态；Storybook 仅证明组合和交互样板。

实现时，筛选后的零结果必须使用 `filtered-empty`，不能复用初始
`empty`。否则用户会误以为系统没有数据，而不是当前条件没有匹配项。

## 6. 参考来源与使用边界

参考资料只借鉴“解决什么问题”，不复制外观：

| 参考 | 借鉴内容 | 不引入 |
| --- | --- | --- |
| svadmin | 色板、字号、圆角和组件行为 | 另一套组件运行时或插画 |
| page patterns | 列表、分组表单、详情、结果页的分区 | 另一套外壳、工作台卡片墙或路由权限 |
| shadcn/ui | 组合方式、语义 token、可读源码 | 第二套色板或无约束的页面自由拼装 |
| Refine | 资源 CRUD、路由和数据状态 | 它的页面皮肤 |
| Metronic / Fuse / Midone | 页面覆盖范围 | 模板式卡片、渐变和营销布局 |

SVAdmin 的无障碍契约、权限边界和状态契约优先级最高。视觉和页面分区以 svadmin 规范为准，组件仍用 shadcn-svelte。

## 8. 工作台、审批和审计

### 工作台

工作台用于连续处理同一个对象的多个阶段，不是把多个页面简单并排。
标准区域为：

```text
WorkspaceLayout
├── summary（当前对象或阶段摘要）
├── primary（主要处理区）
└── secondary（检查器、审计或辅助信息）
```

`primary` 拥有当前任务和主操作，`secondary` 只能补充判断依据或追溯信息。
当对象切换时，主区域和检查器必须同步更新；不能保留上一个对象的审计或
操作按钮。

为工作台提供 `label`，让整个区域具备可识别的 landmark；使用
`mobileOrder` 表达窄屏下的任务优先级，不要通过 CSS 顺序偷偷改变操作顺序。

### 审批

审批页必须同时表达：

- 当前队列：待办或历史；
- 当前记录：申请人、状态、附件和版本；
- 允许的动作：由服务端返回，不由前端猜测；
- 动作结果：成功、版本冲突、契约错误或网络失败。

审批动作必须携带当前版本和幂等键。版本冲突时保留当前记录上下文，
不能把冲突误报为成功。

### 审计

审计时间线是详情页的补充内容，不替代主记录字段。主记录处于 loading、
forbidden 或 error 时，不显示旧的审计事件。空审计必须明确表示“暂无事件”，
不能伪装成加载失败或记录不存在。

这些流程分别使用 `WorkspaceLayout`、`ApprovalCenter` 和 `AuditTimeline`，
并通过以下契约标识进行验收：

```text
data-svadmin-workspace-layout
data-svadmin-approval-center
data-svadmin-approval-state
data-svadmin-audit-timeline
data-svadmin-audit-state
```
